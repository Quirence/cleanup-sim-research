# Первый слой v2: калибровка бюджета пути и baseline-протокол

Дата: 2026-08-21.

Статус: **budget calibration выполнена; nominal path budget не выбран по preregistered gate; найденный edge-effect `lawnmower_collect` исправлен после прогона**.

Этот документ фиксирует первый слой экспериментов для анализа режимов планирования миссии надводного робота при неполной информации о плавающем мусоре. Цель слоя - не выбрать "лучший алгоритм", а проверить, существует ли единый бюджет пути, при котором:

- oracle уже способен почти полностью решить задачу;
- не-oracle режимы еще не насыщаются;
- между режимами есть различимость по AUC;
- сравнение идет по пути, а не по случайному ограничению времени.

## Бюджеты пути

Нормированный показатель:

```text
collection_coverage_ratio = path_budget_m * collection_width_m / area_m2
```

При площади `40000 м2` и ширине сбора `1 м`:

| Path budget | Coverage ratio | Интерпретация |
|---:|---:|---|
| `1200 м` | `3%` | короткая миссия, жесткий дефицит пути |
| `2400 м` | `6%` | средне-короткая миссия |
| `3600 м` | `9%` | прежний nominal, но теперь проверяемый |
| `7200 м` | `18%` | длинная миссия без полного покрытия |

## Gate выбора nominal budget

Бюджет должен был пройти пять условий:

1. `time_budget` у non-oracle режимов не больше `5%`.
2. `oracle_current_physics` собирает медианно не меньше `0.90` в 3 из 4 сценариев.
3. Лучший non-oracle режим не насыщается: медианный `collected_ratio < 0.85` хотя бы в 3 из 4 сценариев.
4. Разница AUC между лучшим и третьим non-oracle режимом не меньше `0.05` хотя бы в 2 сценариях.
5. Если несколько бюджетов проходят, выбирается минимальный.

Фактическое решение:

| Budget | Time-budget rate | Oracle >= 0.90 scenarios | Non-oracle non-saturated scenarios | Distinct AUC scenarios | Pass |
|---:|---:|---:|---:|---:|---|
| `1200` | `0.00` | `1` | `4` | `0` | no |
| `2400` | `0.00` | `4` | `2` | `2` | no |
| `3600` | `0.00` | `4` | `1` | `1` | no |
| `7200` | `0.00` | `4` | `1` | `3` | no |

**Вывод:** единый nominal path budget по заранее заданному правилу не выбран. Поэтому baseline-фаза на `30 seeds` не запускается автоматически: это было бы выбором бюджета задним числом.

## Почему gate не прошел

`1200 м` слишком короткий: oracle достигает медианного сбора `>= 0.90` только в одном сценарии. Значит при таком бюджете даже идеальная информация часто не позволяет решить задачу, и сравнение режимов будет отражать слишком жесткий дефицит пути.

`2400 м` уже достаточно длинный для oracle во всех сценариях, но лучший non-oracle режим насыщается в двух сценариях из четырех. Это делает бюджет полезным для анализа короткой миссии, но слабым как единый nominal для всех сценариев.

`3600 м` и `7200 м` усиливают насыщение динамических сценариев: во многих случаях сильные режимы уже собирают большую часть мусора. Такие бюджеты пригодны для long-horizon анализа и oracle-gap, но хуже подходят для первичного сравнения режимов.

Главный методологический сигнал: **разные гидродинамические сценарии требуют разных масштабов ресурса пути**. Один общий nominal budget может быть менее научно честным, чем режимная карта по normalized coverage.

## Первичные выводы

1. `greedy` больше не выглядит искусственно доминирующим в v2: после исправления физики сбора и метрик он стабильно уступает вероятностным режимам почти во всех сценариях.
2. `lawnmower_collect` является слабым baseline для кластерного мусора при малой ширине сбора: физическое покрытие даже при `7200 м` равно только `18%`.
3. `belief_horizon` остается сильным базовым режимом и часто близок к `adaptive_mission`; это означает, что текущий adaptive-переключатель пока не дает самостоятельного убедительного вклада.
4. `confirmed_route` становится сильным в динамических/возмущенных сценариях при больших бюджетах, но слабее при коротком ресурсе и в статике.
5. Разрыв до `oracle_current_physics` остается большим, особенно в статике: есть пространство для алгоритма, но оно связано не с простым переключением режимов, а с лучшим использованием карты/маршрута/локального сбора.

## Проверка нулевых прогонов

Нулевой сбор обнаружен только у `lawnmower_collect`:

- `strong_drift`: seed `31` и `34` при `1200 / 2400 / 3600 / 7200 м`;
- `weak_drift`: seed `34` при `1200 м`.

Для `7200 м`, `strong_drift`, seed `31` и `34`:

| Seed | Collected | Contacts | Successful captures | Empty goals | Wasted path ratio |
|---:|---:|---:|---:|---:|---:|
| `31` | `0` | `13` | `0` | `71` | `0.977` |
| `34` | `0` | `0` | `0` | `71` | `0.977` |

Причина не в том, что симулятор "забывает" собирать мусор. Режим `lawnmower_collect` физически идет по полосам, но:

- в `strong_drift` суммарная скорость сноса около `0.115 м/с`, то есть примерно `6.9` ширин сборщика за минуту;
- при `7200 м` этот режим идет около `12158 с`;
- из-за положительного сноса по оси `x` и отражающих границ мусор в проблемных seed-ах скапливается около восточной границы `x ~= 199-200 м`;
- маршрут `lawnmower_collect` имеет `coverage_margin_m = 6 м` и ходит между `x=6` и `x=194 м`;
- при ширине сборщика `1 м` такая траектория не достает до приграничной полосы, где оказался мусор.

Это важное ограничение исходного calibration-прогона: `strong_drift` частично создает edge-effect, а не только реалистичное устаревание карты. В статье такие нулевые результаты нельзя трактовать как универсальную слабость равномерного покрытия; их надо описывать как сочетание узкой swept-aperture модели, ограниченного покрытия, сильного дрейфа и отражающих границ.

После диагностики код исправлен: для `lawnmower_collect` `coverage_margin_m` теперь задается как `0.5 * collection_width_m`, а не наследует общий отступ `6 м`. Это позволяет физической полосе сборщика доходить до границы области. Поэтому CSV из `layer1_budget_calibration_2026-08-21` являются **pre-fix диагностикой**; перед финальными выводами нужна повторная calibration-серия.

## Методологическое решение

Baseline на `30 seeds` по одному budget пока **не запускается**, потому что calibration не выбрала budget. Научно честные варианты продолжения:

- перейти от одного nominal budget к regime-map по `collection_coverage_ratio`;
- выбрать отдельные бюджеты для классов сценариев: короткий для динамики и более длинный для static;
- ослабить gate только после явного решения, например заменить критерий насыщения с `0.85` на анализ AUC-gap;
- запустить baseline на нескольких budget-ах и трактовать budget как ось исследования, а не служебный параметр.

Текущий наиболее сильный вариант для статьи: **руководство по выбору режима миссии как функция дефицита пути и динамики мусора**, а не доказательство одного универсального алгоритма.
